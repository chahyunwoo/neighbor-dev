# apps/api 의존성 선택 근거

> 최신 버전을 안 쓴 자리는 이유를 남긴다. 근거가 없으면 다음 세션이
> "왜 낡은 걸 쓰지?" 하고 올렸다가 같은 문제를 다시 밟는다.

## NestJS 는 11 라인이다 (12 아님) — 2026-09-09 실측

`@nestjs/throttler` 가 **NestJS 12 를 지원하는 버전을 아직 내지 않았다.**

```bash
pnpm view @nestjs/throttler versions   # → 6.5.0 이 최신, 7.x 없음
pnpm view @nestjs/throttler@6.5.0 peerDependencies
# → @nestjs/common: '^7.0.0 || ^8.0.0 || ^9.0.0 || ^10.0.0 || ^11.0.0'
```

NestJS 12 로 올리면 이 peer 가 깨진다. throttler 는 **AI 자가진단의 rate limit**
이고 기획서 5절이 "일일 총량 캡이 비용 방어의 본체"라고 못박은 부분이라,
peer 경고를 무시하고 도박할 자리가 아니다.

→ throttler 가 NestJS 12 를 지원하면 그때 함께 올린다. 위 명령으로 확인한다.

## @nestjs/config 는 4.0.4 다 (12.x 아님) — 2026-09-09 실측

버전 체계가 본체와 다르다. 12.0.0 이 최신이고 peer 도 NestJS 11 을 지원하지만
**ESM-only 라 CommonJS 인 이 앱에서 못 쓴다.**

```bash
pnpm view @nestjs/config@12.0.0 type   # → 'module'
pnpm view @nestjs/config@4.0.4 type    # → (없음 = CommonJS)
```

peer 만 보고 12 를 골랐다가 빌드에서 걸렸다:

> TS1479: The current file is a CommonJS module whose imports will produce
> 'require' calls; however, the referenced file is an ECMAScript module

→ **peer 범위만 보지 말고 모듈 형식(`type`)도 본다.** 앱을 ESM 으로 옮기면
그때 12 로 올린다.

## TypeScript 는 6 라인이다 (7 아님) — 2026-09-09 실측

`nest build` 가 TypeScript 7 에서 거부한다:

> The installed TypeScript version (7.0.2) does not expose the programmatic
> compiler API that the Nest CLI requires. TypeScript 7.0 ships the "tsc"
> executable only; the compiler API is expected to return in 7.1.

TS 7.0 은 `tsc` 실행 파일만 내고 프로그래매틱 컴파일러 API 를 빼서, 그 API 에
기대는 도구(Nest CLI 가 그렇다)가 통째로 못 돈다. 7.1 에서 돌아올 예정이다.

⚠️ **`apps/web` 은 TS 7 그대로 둔다.** Next.js 는 자체 컴파일러를 쓰므로
영향이 없다(실측: `pnpm build` 통과). 워크스페이스마다 다른 것이 맞다 —
루트에 하나로 맞추려고 web 까지 내리지 않는다.

→ TypeScript 7.1 이 나오면 api 도 올린다. 확인:
```bash
pnpm view typescript versions --json | python3 -c "import json,sys; print([v for v in json.load(sys.stdin) if v.startswith('7.1')][-3:])"
```
